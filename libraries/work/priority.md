# Job priority

> **v0.6.0 (2026-05-25 / PR 06)** — `JobPriority` enum + `Job.Priority` column.
> RFC 0027 § 12 Amendment 1.

The Job spine gains a first-class `Priority` column for flagging job urgency. Three levels (`Normal`, `High`, `Urgent`); default `Normal`. Surfaced as a colored pill in product UIs (TorqueTech: pill on JobsPage list rows + JobDetail header; mechanic-facing color-coded).

## Why a column on `Job` (not a Custom Field)?

The original RFC 0027 design proposed a Custom Field via `@chthonic/views`'s `entity_field` table. That design didn't survive contact with TorqueTech's existing reflection semantics in `JobEndpoints.Fields.cs:79` — when `EntityField.Entity="Job"` and `AllowMultipleValues=false`, the code reflects-writes to a real Job property via `UpdateEntityProperty`. To avoid that path the seed would need a non-canonical `entity` value, which is semantically muddled — Priority is clearly job-level data.

Custom Field is built for **tenant-configurable** Job-level data. Priority in v1 is **not tenant-configurable**: § 3 of RFC 0027 puts custom levels out of scope (`v1 hard-codes Normal/High/Urgent`). The pattern justification cited the strength of Custom Fields for a feature that deliberately doesn't use that strength.

Lib bumps in this program are routine — adding one column to `Chthonic.Work.Job` is the same kind of additive change as `JobReopen` (PR 19) or `ParentJobId` (PR 07).

See [RFC 0027 § 12 Amendment 1](https://github.com/chthonicsystems/architecture/blob/main/rfcs/0027-priority-urgency.md#12-amendment-1--implementation-diverged-from--2-decision-2026-05-25) for the full reconciliation record.

### Schema delta

```sql
-- Applied consumer-side via TT's RegisterLibsWork060_JobPriority migration.
ALTER TABLE job
    ADD COLUMN priority VARCHAR(20) NOT NULL DEFAULT 'Normal';
CREATE INDEX idx_priority ON job(priority);
```

The lib ships an empty placeholder migration `ChthonicWork_0004_JobPriority` per the [migration coexistence pattern](../../platform/library-consumption.md#migration-coexistence). The consumer (TorqueTech) inserts the placeholder ID into `__EFMigrationsHistory` and owns the actual DDL.

Existing rows acquire `'Normal'` automatically via the column DEFAULT. Zero backfill SQL needed.

## Sort caveat (lexicographic vs ordinal)

`Priority` stores VARCHAR display strings, so an unguarded `ORDER BY priority` is **lexicographic** — wrong:

```
'High' < 'Normal' < 'Urgent'   (alphabetical)
```

Consumers that want priority-ordered sort must use a CASE expression mapping the display strings to ordinals. The convention is `Urgent=2, High=1, Normal=0`. In EF Core 9, the cascaded ternary translates to SQL CASE:

```csharp
query = query
    .OrderByDescending(j => j.Priority == JobPriority.Urgent ? 2 :
                            j.Priority == JobPriority.High   ? 1 : 0)
    .ThenByDescending(j => j.UpdatedAt);
```

This matches the precedent for `Status` (also stored as a HasConversion'd display string).

## AutoCommentGenerator hook

`TrackPriorityChange` mirrors the diff-vs-write split of `TrackJobChanges` + `AddJobUpdateComment`:

```csharp
var commentText = commentGenerator.TrackPriorityChange(job, newPriority, actorName);
if (commentText != null)
{
    job.Priority = newPriority;
    job.UpdatedAt = DateTime.UtcNow;
    await db.SaveChangesAsync();
    await commentGenerator.AddPriorityChangeComment(jobId, userId, job.SystemId, commentText);
}
```

The format is `"Priority changed from {old} to {new} by {actorName}"` — symmetric with the existing `Status`-change comment shape.

## Consumer guidance

For products consuming `@chthonic/work` v0.6.0+:

- **Default behaviour is correct out of the box.** New jobs default to `Normal`; existing jobs acquire `Normal` via column DEFAULT on ALTER TABLE.
- **No tier-gating recommended.** Per [RFC 0027 § 3](https://github.com/chthonicsystems/architecture/blob/main/rfcs/0027-priority-urgency.md), this is an all-tier feature — a flag would be dead plumbing.
- **Validate input strictly.** Use `Enum.TryParse + Enum.IsDefined` to reject numeric backdoors (`Enum.TryParse<JobPriority>("123", ...)` returns true with `(JobPriority)123`).
- **Sort via CASE.** Don't rely on lexicographic ordering of the VARCHAR — use the ordinal mapping above.
