# Version policy

Every Chthonic library follows **SemVer 2.0.0** with **Conventional Commits**. Versions are immutable; once a tag is pushed, that version is frozen on GitHub Packages.

## Pre-extraction baseline

Every library currently lives at `0.x.y` (pre-1.0). The major version `0` indicates the platform is in early stabilisation; **any minor bump may include breaking changes**, but every breaking change is documented in the library's `CHANGELOG.md`.

A library moves to `1.0.0` once **the first product GAs on it**. Until then, breaking changes are explicit but cheap (every consumer is internal).

## SemVer rules

| Bump | Trigger | Examples |
|---|---|---|
| `MAJOR` (X.y.z) | Backward-incompatible API change | Removed public method; renamed entity property; changed schema column type |
| `MINOR` (x.Y.z) | Backward-compatible feature add | New service method; new entity (no FK from existing); new endpoint |
| `PATCH` (x.y.Z) | Backward-compatible fix | Bug fix; doc-only update; non-functional refactor |

In `0.x.y`: a `MINOR` bump may carry breaking changes. Read the CHANGELOG.

## Conventional Commits

Every commit message follows the [Conventional Commits 1.0](https://www.conventionalcommits.org/en/v1.0.0/) format:

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

Common types:

| Type | Use |
|---|---|
| `feat:` | New feature (drives MINOR bump) |
| `fix:` | Bug fix (drives PATCH bump) |
| `docs:` | Documentation only |
| `refactor:` | Internal refactor, no public-API change |
| `test:` | Test-only change |
| `chore:` | Build / CI / tooling |
| `feat!:` or footer `BREAKING CHANGE:` | Breaking change (drives MAJOR bump pre-1.0; MINOR pre-1.0) |

Scope (optional): the library subsystem affected. Examples:

```
feat(rbac): add role inheritance
fix(auth): JWT validation on expired tokens
docs(consumption): add nuget.config example
```

## Release automation

Each library's `.github/workflows/release.yml` is fired by tag push (`git tag v<X.Y.Z> && git push --tags`). The workflow:

1. Validates the tag matches `Directory.Build.props` `<Version>` (.NET) or `package.json` `version` (npm).
2. Runs the full xUnit + vitest suites.
3. Builds `dotnet pack` (`.nupkg`) and `npm pack` (`.tgz`).
4. Pushes both to GitHub Packages.

**Tag naming:** `v<major>.<minor>.<patch>` (e.g. `v0.5.0`). Always SemVer-compliant. No `-pre`, `-rc`, etc. unless explicitly using SemVer pre-release suffixes.

## CHANGELOG

Each library carries a `CHANGELOG.md`. Hand-curated or generated by `release-please` from Conventional Commits. The CHANGELOG entry for `vX.Y.Z` MUST exist before the tag is pushed.

Minimum CHANGELOG entry shape:

```markdown
## [0.5.0] — 2026-05-19

### Added
- `IFeatureGateService.IsEnabledAsync(string flag, int? systemId)` — per-tenant flag check.

### Changed
- `SystemPackage.MaxUsers` removed; numeric quotas live on `tier_limit` rows now (BREAKING).

### Fixed
- Race condition in `QuotaUsage.IncrementAsync` under concurrent calls.
```

## Bumping a library version (consumer side)

When TorqueTech (or another consumer) consumes a new library version:

```bash
# 1. Bump the package reference.
cd api
sed -i '' 's|"Chthonic.Identity" Version="0.1.3"|"Chthonic.Identity" Version="0.1.4"|' TorqueTech.Api.csproj

# 2. Restore + build + test locally.
cd ..
./dev-start.sh                 # full local verification

# 3. Verify on beta.
git checkout -b bump/identity-0.1.4
git commit -am "chore: bump @chthonic/identity 0.1.3 → 0.1.4"
gh pr create --title "Bump @chthonic/identity 0.1.3 → 0.1.4" \
             --body "CHANGELOG: <link to library CHANGELOG>"

# 4. Merge after beta CI passes.
```

## Bumping a library across BREAKING change

For a major bump (e.g. `0.4.x` → `0.5.0` with a schema rename):

1. **Author the upstream change in the library repo.** Open a PR there; tag a `0.5.0` release.
2. **Author an RFC amendment** in `chthonicsystems/architecture/rfcs/<NNNN>-...md` § Change History describing the breaking change and consumer migration steps.
3. **Open a TT PR** that bumps the package ref, runs the consumer-side migration, updates `__EFMigrationsHistory` if the lib's `0001_Initial` schema rename runs.
4. **14-day dual-write window for data-shape changes.** If the change writes to two columns in parallel for a time, document the dual-write in the RFC + the consumer PR description.
5. **Verify on local + beta** before merging to TT main.
6. **Watch monitoring** for the first 24h after prod deploy.

## Version pinning discipline

**Always exact-pin** library versions in consumer manifests:

```xml
<!-- ✅ Correct -->
<PackageReference Include="Chthonic.Identity" Version="0.1.4" />

<!-- ❌ Wrong — never use ranges or carets -->
<PackageReference Include="Chthonic.Identity" Version="0.1.*" />
<PackageReference Include="Chthonic.Identity" Version="^0.1.4" />
```

```json
{
  "dependencies": {
    "@chthonicsystems/identity": "0.1.4"
  }
}
```

```json
{
  "dependencies": {
    "@chthonicsystems/identity": "^0.1.4"
  }
}
```

**Why:** Range pins cause two consumers running on the same prod to potentially run different library versions, which silently breaks contracts (e.g. one writes the new schema; the other reads with the old EF mapping → null reference).

## Yanking a release

GitHub Packages doesn't truly delete a published version, but a version can be marked as deprecated. To pull a bad release:

1. **Publish a higher patch version with the fix.**
2. **Open an issue in the library repo** with a `deprecated:<bad version>` label.
3. **Update the CHANGELOG** entry for the bad version with a "DEPRECATED — use 0.X.Y+1" note.
4. **Bump consumers off the bad version ASAP.**

The platform doesn't currently use NuGet's deprecation feature — the convention is "publish + announce + bump consumers".
